## 1. 概要

本プロジェクトは、Pythonを使用して開発された、歩行者シミュレーション環境です。特に「歩きスマホ」が歩行者の行動に与える影響を可視化し、パラメータを変えながらその危険性を分析することを目的としています。舞台は歩道（車道を挟んで対向2車線）で、危険性がひと目で追いやすいよう、あえて単純な二方向のすれ違い構図にしています。

## 1.1. ファイル構成

- **`sim_core.py`**: 物理演算・衝突/柱接触/よろめき/ニアミスの検出ロジック本体。Pygame・Ursinaどちらにも依存しない純粋なnumpyコード。2D版・3D版の両方から使われる「共通エンジン」。
- **`simulation.py`**: 2D版（Pygame）。`sim_core`の状態を上から見た2D画面に描画する。
- **`simulation_3d.py`**: 3D版（[Ursina Engine](https://www.ursinaengine.org/)、試験導入）。同じ`sim_core`の状態を3D空間に描画する。単独で `python simulation_3d.py --p_phone=0.3 --spawn_rate=1.0` のように起動できる（矢印キーで視点回転、+/-でズーム、Spaceで一時停止）。
- **`control_panel.py`**: GUIコントロールパネル（tkinter）。現状は2D版(`simulation.py`)を起動する。
- **`analysis_plot.py`**: リアルタイム分析グラフ（matplotlib）。

シミュレーション本体は、以下の3つの独立したプログラムが連携して動作する構成が基本です。

1.  **コントロールパネル (`control_panel.py`):** シミュレーションの各種パラメータ（歩きスマホ率、歩行者の発生頻度など）を設定し、シミュレーション本体の起動・停止を管理するGUIアプリケーションです。
2.  **シミュレーション本体 (`simulation.py`):** Pygameを利用して、歩行者の動きを実際に描画するウィンドウです。コントロールパネルから受け取ったパラメータに基づいて動作し、現在の状況をリアルタイムでファイルに出力します。
3.  **リアルタイム分析 (`analysis_plot.py`):** シミュレーション本体が出力するデータを読み込み、平均速度や衝突率などの指標をグラフでリアルタイムに可視化するウィンドウです。

## 2. 主な機能

- **分離されたUI:** 操作パネルと分析画面をシミュレーション描画から分離し、安定した操作性と高い拡張性を実現。
- **パラメータの動的変更:** GUIを通じて、シミュレーションをリスタートするだけで簡単に実験条件を変更可能。
- **論文に基づく物理モデル:** 歩きスマホ時の「反応時間の遅延」「視野角の狭窄」「速度低下」や、通常歩行者同士の強い回避傾向など、学術研究に基づいたパラメータをモデルに組み込んでいます。
- **詳細なデータ分析:** 「衝突」「柱・什器への接触」「よろめき（転倒リスク）」の3指標を歩行者のタイプ別に算出し、グラフで比較・可視化します。
- **多様な危険性の可視化:** 歩行者同士の衝突（赤/黄）、柱への接触（オレンジ）、よろめき（紫）を、それぞれ発生地点にマーカーで一定時間表示し、危険箇所を直感的に把握できます。
- **視覚的にわかりやすいレイアウト:** 車道を挟んだ2車線の歩道で、左右に流れる対向2方向の人流のみとしたシンプルな構図。1人1人のすれ違い・接近・衝突が追いやすい。街灯・標識ポールも数本配置し、柱への接触も再現。

## 3. 使い方

1.  **依存ライブラリのインストール:**
    ターミナル（コマンドプロンプト）でこのフォルダに移動し、以下のコマンドを一度だけ実行します。
    ```bash
    pip install -r requirements.txt
    ```

2.  **コントロールパネルの起動:**
    以下のコマンドで、操作用のGUIウィンドウを起動します。
    ```bash
    python control_panel.py
    ```

3.  **シミュレーションの開始:**
    表示された「シミュレーション・コントロールパネル」でパラメータを調整し、「シミュレーション開始 / 再起動」ボタンを押します。これにより、シミュレーションウィンドウと分析ウィンドウが自動的に起動します。

4.  **シミュレーションの停止:**
    コントロールパネルの「シミュレーション停止」ボタンを押すか、ウィンドウを閉じることで、関連する全てのウィンドウが同時に終了します。

## 4. 設計と実装における課題と工夫

本シミュレーションの開発では、いくつかの技術的な課題に対し、以下のような工夫で対応しました。

### 課題1: GUIの日本語表示問題

- **問題点:** 当初、PygameのGUIライブラリ(`pygame-gui`)を使用していましたが、日本語フォントの扱いがPC環境に強く依存し、文字化けなどの問題が安定して解決できませんでした。
- **工夫と解決策:** ご利用者からのフィードバックを受け、PygameベースのGUIを断念しました。代わりに、Python標準のGUIライブラリ`tkinter`でコントロールパネルを、グラフ描画ライブラリ`matplotlib`で分析画面を、それぞれ独立したプログラムとして作成するアーキテクチャに変更しました。これらのライブラリは日本語フォントの扱いに優れており、環境に依存しない安定した日本語表示を実現できました。

### 課題2: リアルタイムでのプロセス間連携

- **問題点:** コントロールパネル、シミュレーション、分析画面が3つの別々のプロセスとして動作するため、これらを連携させる必要がありました。特に、分析画面がシミュレーションの状況をリアルタイムに知るための仕組みが求められました。
- **工夫と解決策:**
    - **制御 (コントロールパネル → シミュレーション):** Pythonの`subprocess`モジュールを利用しました。コントロールパネルは、設定されたパラメータをコマンドライン引数として`simulation.py`に渡し、新しいプロセスとして起動・停止します。これにより、複雑なリアルタイム通信なしに、確実な制御を実現しています。
    - **データ共有 (シミュレーション → 分析):** 最もシンプルで堅牢な方法として、ファイルベースの通信を採用しました。シミュレーション側が現在の主要な指標（平均速度、衝突回数など）を`live_data.json`というファイルに非常に短い間隔で書き出し、分析側がそのファイルを定期的に読み込んでグラフを更新します。これにより、プロセス間での複雑な同期処理を回避しつつ、ほぼリアルタイムのデータ共有を可能にしました。

### 課題3: 衝突の連続カウント問題

- **問題点:** 当初の衝突判定では、2体のエージェントが重なっている間、毎フレーム衝突をカウントしてしまい、一度の接触が数百回の衝突として計測される問題がありました。
- **工夫と解決策:** 衝突状態を管理する仕組みを導入しました。前のフレームで既に接触していたエージェントのペアを記憶しておき、現在接触しているペアが「新規」の場合にのみ衝突イベントとしてカウントします。これにより、一度の接触は正確に「1回」として計測されるようになり、データの信頼性が大幅に向上しました。
